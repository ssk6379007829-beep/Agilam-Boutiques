## 1. Executive summary

### Current state

The SEO *engineering* on this site is, genuinely, better than most funded
marketplaces. A Vercel edge middleware server-injects title, description,
canonical, Open Graph, Twitter, robots directives, JSON-LD and a crawlable
`<noscript>` body into the SPA shell before a byte of JavaScript ships. There is
a split sitemap index, a Google Merchant Center RSS feed, one-hop canonical-host
301s, LCP preloading, Supabase on-the-fly WebP with `srcset`, and a regression
suite (`npm run verify:seo`). Nine of the schema types Google actually uses are
already emitted. None of that needs rebuilding.

The problem is what is inside the machine.

### Top 3 opportunities

1. **Local/regional intent is a free asset you are not spending.** All ten
   approved boutiques are in Tamil Nadu — Tiruppur, Erode, Dharapuram, Dindigul,
   Coimbatore, Oddanchatram, Pethapampatti. `ClothingStore` schema, per-city
   `/boutiques/:city` pages and city landing copy already exist in code.
   "Boutiques in Coimbatore"-class queries are winnable now, at 21 products,
   in a way that "buy cotton kurta set online" is not.
2. **The catalogue's own text is the cheapest ranking input you own.** Four of
   21 products have descriptions under 150 characters, one has none, and several
   titles ("Monsoon Lagoon", "Gem Violet", "Raw Silk") carry no searchable noun.
   Seller-side copy quality is a product feature, not a content project — fixing
   it at the Add-Product form fixes every future product for free.
3. **The Merchant Center feed already exists and is correctly formed.** Shopping
   free listings are the fastest path to buyer discovery at low inventory,
   because they do not require domain authority. It is blocked today only by the
   test-priced rows (§2, T2).

### Top 3 risks

1. **A latent de-indexing bug fires at ~40 active products** (T1). Category,
   occasion, fabric, colour and budget landing pages resolve from an *unordered*
   40-row read while the sitemap enumerates them from a 5,000-row read. Above 40
   products the two disagree, and facets whose stock falls outside the arbitrary
   first 40 rows begin serving `noindex` soft-404s at URLs the sitemap is
   actively advertising. You are at 21. This is the single most important item
   in this report, because the entire strategy is "grow inventory".
2. **Pan-India is not reachable in 12 months at this inventory.** You chose it,
   so this report delivers it in full — but honestly: 21 SKUs cannot compete
   with Myntra/Ajio/Mirraw/Utsav on head category terms, and no amount of
   technical work changes that. The plan below therefore targets pan-India
   *long-tail and shopping surfaces* first, with the head terms as the 12-month
   destination and inventory as the explicit gate.
3. **Structured data promises things the platform no longer guarantees** (S1).
   `src/lib/schema.ts` hardcodes a 7-day free return and 1–2 day handling on
   every product, while migration 0078 made the return window and dispatch days
   **the seller's**. That is a rich-result eligibility risk and a consumer
   promise you may not be able to keep.

## 4. What is already right — do not "fix" these

Listing these explicitly so a future contributor does not undo them:

- **Edge SSR of metadata.** The single biggest custom-stack trap — a CSR React
  app serving crawlers an empty `<div id="root">` — is already solved. Titles,
  descriptions, canonicals, OG, JSON-LD **and** a `<noscript>` body with real
  product links and prices are in the raw HTML.
- **One-hop canonical-host 301s.** `agilam-boutiques.vercel.app` and
  `www.mangaimart.com` previously served the whole catalogue as self-canonical
  duplicates. Fixed, and the fallback in `CANONICAL_HOST` makes forgetting
  `VITE_SITE_URL` survivable.
- **Preview deploys are `Disallow: /` with `x-robots-tag: noindex`.**
- **Query strings are stripped from the canonical** (`middleware.js`: `canonical
  = origin + pathname`). This neutralises every UTM and tracking parameter for
  free. Off-the-shelf platforms need a plugin for this.
- **`AggregateRating` is emitted only when a real rating exists.** Correct, and
  the reason it is currently absent everywhere is data, not code.
- **Merchant feed 503s rather than serving empty** on a failed DB read — an empty
  feed delists the whole catalogue in Merchant Center.
- **Images**: Supabase `render/image` with WebP negotiation, a deliberately short
  width ladder and `srcset`. Better than most Shopify themes.
- **Fonts loaded with the `media="print"` swap**, immutable asset caching, HSTS
  preload, LCP preload on `/`.

## 5. Per-pillar detail

### 5.1 Technical SEO & crawlability

**Indexation health.** Cannot be stated without GSC (§9). The counts to compare
once you export: submitted (sitemap total ≈ 21 products + 10 boutiques + ~30
facets + ~7 cities + ~12 static ≈ **80 URLs**) vs indexed vs crawled-not-indexed.
At this size, "crawled – currently not indexed" on facet pages is the metric that
tells you whether thin content is being rejected.

**Crawl depth.** Home → `/collections` → `/collections/kurta-sets` → product = 3
clicks. Good. The `<noscript>` hub prerenders are what make it real for a bot.

**T1 — the facet resolver. Fix this first.**

Today (`middleware.js:1269`):

```js
const attempt = await dbProductsTry(
  (cols) => `products?select=${cols}&status=eq.active&deleted_at=is.null&limit=40`
);
const items = attempt.rows.filter((p) => { /* facet match in JS */ });
if (!items.length) return notFoundMeta();   // ← noindex soft-404
```

Two independent defects: the read is capped at 40 **and** has no `ORDER BY`, so
which 40 rows come back is whatever Postgres feels like returning. Push the
filter into PostgREST so the cap applies *after* the facet, not before it:

```js
// Facet → PostgREST predicate. `ilike` because sellers type free text:
// "office wear", "SAREES", "Loomed  Cotton" are all the same term to a slug.
const FACET_FILTER = {
  category: (t) => `category=ilike.${encodeURIComponent(t)}`,
  occasion: (t) => `occasion=ilike.${encodeURIComponent(t)}`,
  fabric:   (t) => `fabric=ilike.${encodeURIComponent(t)}`,
  colour:   (t) => `color=ilike.${encodeURIComponent(t)}`,
};

async function metaForCategory(kind, slug, origin) {
  const ceiling = kind === 'budget' ? budgetCeiling(slug) : null;
  if (kind === 'budget' && ceiling === null) return notFoundMeta();

  // A slug cannot be reversed to the seller's exact spelling, so resolve the
  // term from the facet index first (one cheap read of a narrow projection),
  // then fetch that facet's products with the filter in SQL.
  const filter = kind === 'budget'
    ? `price=lte.${ceiling}`
    : FACET_FILTER[kind](await termForSlug(kind, slug));   // see below

  const attempt = await dbProductsTry(
    (cols) => `products?select=${cols}&status=eq.active&deleted_at=is.null` +
              `&${filter}&order=created_at.desc&limit=60`
  );
  if (!attempt.ok) return null;          // DB blinked ≠ page does not exist
  const items = attempt.rows;
  if (!items.length) return notFoundMeta();
  …
}
```

`termForSlug` reuses the same narrow `select=category,occasion,fabric,color`
read the sitemap already does at `middleware.js:1642`, so the facet vocabulary is
resolved from the *whole* catalogue exactly as the sitemap resolves it — which is
what makes the sitemap and the page agree by construction rather than by
coincidence. Cache it behind the existing 1500 ms abort.

**Regression test to add to `scripts/verify-seo.mjs`:**

```js
// Every facet URL the sitemap advertises must resolve to an INDEXABLE page.
// This is the assertion that would have caught T1.
const sitemap = await get('/sitemap-pages.xml');
const facetUrls = [...sitemap.matchAll(/<loc>([^<]*\/(collections|occasions|fabrics|colours|budget)\/[^<]+)<\/loc>/g)]
  .map((m) => new URL(m[1]).pathname);
for (const path of facetUrls) {
  const html = await get(path);
  assert(!/name="robots" content="noindex/.test(html),
    `${path} is in the sitemap but serves noindex`);
}
```

**T3 — real 404 status.** In the middleware's final return:

```js
const headers = new Headers({ /* … as today … */ });
if (preview || isNoIndex(pathname) || meta?.noindex) headers.set('x-robots-tag', 'noindex, nofollow');
// A page whose subject does not exist must say so in the status line, not only
// in a meta tag. The edge builds this Response, so it can.
return new Response(injected, { status: meta?.notFound ? 404 : 200, headers });
```

Keep the `noindex` as well — belt and braces, and it covers crawlers that read
the body before the status.

**Faceted navigation — the exact rules.** This is where custom platforms
usually fail and where you are mostly already right. Codify it as:

| URL shape | Crawl | Index | Canonical | Sitemap |
|---|---|---|---|---|
| `/collections/<category>` | ✅ | ✅ if ≥1 live product | self | ✅ |
| `/occasions/<occasion>` | ✅ | ✅ if ≥3 live products **and** term ≠ "for all" | self | ✅ if indexed |
| `/fabrics/<fabric>` | ✅ | ✅ if ≥3 live products **and** term is in the controlled vocabulary | self | ✅ if indexed |
| `/colours/<colour>` | ✅ | ✅ if ≥3 live products **and** colour is one of ~14 base colours | self | ✅ if indexed |
| `/budget/under-<rung>` | ✅ | ✅ if ≥3 live products | self | ✅ if indexed |
| `/boutiques/<city>` | ✅ | ✅ if ≥2 approved boutiques | self | ✅ if indexed |
| `/shop` | ✅ | ✅ | self | ✅ |
| `/shop?<any params>` | ❌ | ❌ | `/shop` | ❌ |
| `/shop/filter`, `/shop/sort` | ❌ | ❌ | `/shop` | ❌ |
| `/search`, `/*?q=` | ❌ | ❌ | — | ❌ |
| Two facets combined (`/collections/sarees?color=red`) | ❌ | ❌ | `/collections/sarees` | ❌ |
| `?utm_*`, `?gclid`, `?fbclid` | ✅ | ✅ | query-stripped self | ❌ |

The "≥3 products" threshold is the one line that prevents the classic marketplace
faceted-nav blowout. **On Shopify this needs an app or `theme.liquid` surgery,
and on WooCommerce a Yoast/RankMath rule set; here it is a boolean in
`metaForCategory` and a matching predicate in `sitemapPagesXml`. Keep the two in
one shared function so they cannot drift** — which is exactly the failure mode of
T1.

robots.txt additions:

```
# Filtered/sorted result sets — the facet landings are the indexable equivalents.
Disallow: /shop?*

# Un-block SEO crawlers. Blocking these does not stop scraping; it only stops
# us auditing our own site and researching competitors' link profiles.
# (delete the AhrefsBot and SemrushBot blocks)
```

**JS rendering.** Already handled — this is the trap and you are through it.
Verify per release: `curl -s https://mangaimart.com/collections/kurta-sets | grep -c '<a href="/products/'`
should be > 0, and the same for `₹` to confirm prices are in raw HTML.
Also run the URL Inspection tool's "View crawled page" on one product URL.

**Core Web Vitals.** No field data available (§9). The build is well set up —
async fonts, immutable assets, WebP `srcset`, LCP preload on `/`. Two things to
check once CrUX data exists:

- **LCP**: `lcpPreload` only fires on `/` (`resolveMeta`: `lcpImage: pathname === "/"`).
  Product pages — the pages that will receive organic traffic — get no preload
  for their hero image. Extend `lcpImage` to `metaForProduct`. Low effort, likely
  meaningful.
- **CLS**: the `<noscript>` prerender block is injected *before* `#ag-boot` and
  removed when React mounts. Confirm it is `display:none` in the rendered
  viewport or it will cause a layout shift on slow connections. Verify in
  Lighthouse with JS enabled.
- **INP**: infinite scroll on `Results.tsx` is the likeliest INP offender.

**HTTPS / status codes / redirects.** HSTS with preload is set in `vercel.json`.
Legacy `/buyer/*` paths 301 to clean equivalents, and the non-canonical-host and
legacy rewrites are resolved *together* so there is no chain. Verify with
`curl -sIL https://www.mangaimart.com/buyer/results` — expect exactly one 301
to `https://mangaimart.com/shop`.

**International / hreflang.** Pan-India English: **no hreflang needed, and none
is emitted.** Correct. `<html lang="en-IN">` and `og:locale: en_IN` are right.
Do not add hreflang unless Tamil ships.

**Crawl budget.** Irrelevant at ~80 URLs. It becomes relevant the moment
programmatic category × city pages land in Phase 3 — that is when the §5.1
faceted rules stop being hygiene and start being load-bearing.

### 5.2 Keyword research & mapping

**No search-volume figures appear in this report.** I have no keyword tool data
and will not invent it. What follows is the *structure* — intents, page-type
mapping and cannibalisation rules. Volumes must be attached from GSC (your own
impressions, which is the best source you have) plus one of Ahrefs/Semrush/
Keyword Planner before any of it is committed to.

**Intent → page type. The rule: never point two intents at one URL.**

| Intent | Query shape | Correct page type | Live example |
|---|---|---|---|
| Transactional, head | "cotton kurta set online" | Category landing | `/collections/kurta-sets` |
| Transactional, modified | "cotton kurta set under 2000" | Budget × category (Phase 3) | — |
| Transactional, local | "boutiques in Coimbatore" | City directory | `/boutiques/coimbatore` |
| Transactional, brand+ | "MangaiMart sarees" | Category landing | `/collections/sarees` |
| Navigational, seller | "<boutique name> Tiruppur" | Boutique profile | `/boutique/<slug>` |
| Product-specific | "raw silk crop top pleated skirt" | Product page | `/products/…` |
| Commercial investigation | "cotton vs modal kurti which is better" | Buying guide | **missing** |

### 5.3 On-page optimization

**Title templates.** Current templates (in `middleware.js` / `src/lib/pageMeta.ts`,
mirrored — change both) are already good. Keep:

```
Product   : {title} · MangaiMart
Category  : {Heading} Online — Buy from Verified Indian Boutiques
Budget    : Ethnic Wear Under ₹{n} — Buy from Verified Indian Boutiques
City      : Boutiques in {City} — Verified Ethnic Wear Shops
Brand pages: lead with "MangaiMart" (titleWithBrand already handles this)
```

The **product** template is the weak one, and the weakness is the data not the
template: `Gem Violet · MangaiMart` is 22 characters of which zero are a search
term. Enrich it at render time from fields you already have:

```
{title} — {fabric} {category} | {boutique}, {city} · MangaiMart
→ "Gem Violet — Modal Cotton Kurti | <boutique>, Tiruppur · MangaiMart"
```

Cap at ~60 characters before the brand, and skip any component that is already a
substring of the title (the same containment check `titleWithBrand` already does).

**Meta description templates.** The category templates are strong and already
data-driven ("21 pieces from 6 verified boutiques, from ₹899"). Product
descriptions should follow the same measured pattern:

```
{title} from {boutique}, {city}. {fabric} · {colour} · sizes {sizes}.
₹{price}. Chat directly with the shop. Delivery across India.
```

**Heading hierarchy.** The `<noscript>` prerenders emit exactly one `<h1>`
(`middleware.js`: `<h1>${heading}</h1>`). Verify the *React* render matches —
a mismatch between the prerendered `h1` and the client-rendered one is a
custom-stack-specific trap that no Shopify theme can produce. Check with
`document.querySelectorAll('h1').length === 1` on each page type.

**Category copy strategy.** Currently zero words of unique editorial on any
category page — the description meta is generated, the body is a product grid.
Add per-category:

- **Above the fold:** 1–2 sentences, unique, human-written, containing the head
  term naturally. Sits under the `h1`, above the grid.
- **Below the fold:** 150–250 words — what to look for in this garment, how the
  boutiques in this category differ, sizing/care notes, 3–5 contextual links to
  related categories and to the buying guide that supports it.

Store it in a `category_copy` table keyed by facet kind + slug so the edge can
inject it into the prerender. **This is where a custom platform beats Shopify:**
you control the prerender, so the copy is in the raw HTML rather than in a
theme section that ships after hydration.

**Product descriptions.** You have no manufacturer-copy duplication problem —
every piece is one-off boutique stock, which is a structural SEO advantage over
every dropshipper. The problem is *absence*: 1 empty, 4 under 150 characters.
Fix at the source, in the seller Add-Product form:

- Minimum 300 characters, enforced, with a live counter.
- Structured prompts rather than a blank box: *fabric & feel · fit & sizing ·
  styling suggestion · care instructions*. Four short answers beat one blank
  textarea by a wide margin, and they produce naturally keyword-rich prose.
- Title guidance: "Describe the piece, not the mood — *Gem Violet Modal Cotton
  Kurti*, not *Gem Violet*." With a soft warning when the title contains no term
  from `src/lib/vocabulary.ts`.
- Spell-check the vocabulary fields (`Kota cottan` → `Kota Cotton`) — a
  misspelling in the title becomes a permanent misspelling in the slug.

**Image SEO.** Compression and format are solved. The gaps:

- **Alt text**: audit every `<img>` in the buyer console. Product images should
  be `alt="{title} — {fabric} {category} from {boutique}"`, not `alt=""` or
  `alt="product"`. Verify: `grep -rn 'alt=' src/pages/buyer/ProductDetail.tsx`.
- **Filenames**: Supabase Storage keys are UUIDs. Google reads image filenames.
  Rename on upload to `{product-slug}-{n}.jpg` in `src/lib/uploadImage.ts` — a
  one-line change that applies to all future uploads.
- **Image sitemap**: `sitemapProductsXml` already declares the
  `xmlns:image` namespace (`middleware.js:2115`). Confirm `<image:image>`
  entries are actually emitted per product; if not, that is a cheap win for the
  image pack.

**Out-of-stock handling.** Measured: 2 of 21 products are out of stock. Current
behaviour is correct — `availabilityOf(product.stock)` emits
`schema.org/OutOfStock` and the page stays live and indexable. **Keep this.**
Codify the full policy:

| State | Page | Status | Index | Schema |
|---|---|---|---|---|
| Out of stock, returning | Keep live | 200 | index | `OutOfStock` |
| Out of stock, permanent (one-off piece sold) | Keep live, show "sold" + link 4 similar | 200 | index | `SoldOut` |
| Deleted by seller (`deleted_at`) | 410 to be strict, or 301 to its category | 410/301 | — | — |
| Boutique deactivated | 301 all its products to the category | 301 | — | — |
| Never existed | 404 (fix T3) | 404 | noindex | — |

The "permanent, one-off piece" row matters more here than on a normal store:
almost your entire catalogue is single-quantity boutique stock, so pages will go
permanently out of stock as a matter of routine. Keeping them indexed with
`SoldOut` plus similar-item links retains the link equity and the long-tail
traffic; 404-ing them would throw away most of your indexed surface over time.

### 5.4 Site architecture & internal linking

Taxonomy is sound: five orthogonal facets (category, occasion, fabric, colour,
budget) plus a boutique dimension. Breadcrumbs are emitted as `BreadcrumbList`
on every facet, product and city page.

**Gaps:**

1. **No crawlable pagination (A1).** `Results.tsx` uses `IntersectionObserver`.
   Add `?page=N` that the router honours, and emit in the `<noscript>` body:
   ```html
   <nav><a href="/collections/kurta-sets?page=2" rel="next">Next page</a></nav>
   ```
   Canonical: **self-referencing on each page** (`/collections/kurta-sets?page=2`
   canonicals to itself, *not* to page 1 — Google deprecated `rel=prev/next` as
   an indexing signal in 2019, and canonicalising page 2 to page 1 hides page 2's
   products). Note this requires an exception to the "canonical strips the query"
   rule in `middleware.js` — the one query parameter that must survive.
2. **Orphan risk.** `/colours/*` and `/budget/*` pages are reachable from the
   sitemap and from `CategoryLanding` cross-links only. Add a facet nav block to
   the `/collections` hub prerender listing every indexable facet URL, so no
   landing page is sitemap-only. (The code comment at `middleware.js:1495`
   documents this exact lesson for `/collections`, `/occasions` and `/fabrics` —
   apply it to colours and budget too.)
3. **Contextual links.** Product pages should link to: the boutique, the category,
   the fabric facet, and 4 related products. Verify which of these are in the
   *prerendered* HTML, not just the React render.
4. **Hub pages.** `/collections` is the only true hub. Add `/fabrics` and
   `/occasions` index pages — they are facet prefixes with no hub today.

### 5.7 E-E-A-T & trust

**Reviews are the gap that matters (E1).** One review against 27 orders.
That is a ~4% review rate, and it costs you `AggregateRating` on every product,
review stars in the SERP, and conversion.

Build the request flow: a Resend email 3 days after delivery status flips (the
templates directory and Resend integration already exist), one reminder at day
10, deep-linked to a one-click star rating. Target ≥25% review rate. **Do not**

**Already strong:** nine policy pages exist (`src/data/policies.ts`) — delivery,

**Gaps:**

- **S1 — fix the return promise in schema.** Per-seller values, not hardcoded:
  ```json
  {
    "@type": "Offer",

      "@type": "MerchantReturnPolicy",
      "applicableCountry": "IN",
      "returnPolicyCategory": "https://schema.org/MerchantReturnFiniteReturnWindow",
      "merchantReturnDays": 7,
      "returnMethod": "https://schema.org/ReturnByMail",
      "returnFees": "https://schema.org/FreeReturn"
    },

      "@type": "OfferShippingDetails",
  ```

## 8. Where this differs from Shopify / WooCommerce

Called out because every fix above is hand-rolled:

| Concern | Shopify / Woo | MangaiMart |
|---|---|---|
| Meta & schema | App/plugin (Yoast, RankMath, Smart SEO) | `middleware.js` + `src/lib/schema.ts`, edge-injected. **Two mirrored copies — change together** |
| Canonicals | Platform-generated, hard to override | `canonical = origin + pathname`, query stripped. You own it |
| Faceted nav | Platform emits `?filter.v.*` URLs you must suppress | You choose which facets become URLs at all — a real advantage, and T1 is the cost of it |
| Sitemaps | Auto, uneditable | Hand-built from live SQL. Freshness is guaranteed; **consistency with the page is not** (T1) |
| Pagination | `?page=N` free | Does not exist. Must be built (A1) |
| Robots.txt | `robots.txt.liquid` / plugin | Generated in the edge. Fully controllable |
| 404s | Real 404 from the platform | SPA shell at 200 — must be set explicitly (T3) |
| Product copy | Manufacturer duplication is the usual problem | One-off boutique stock: no duplication problem, but an *absence* problem |
| Blog | `/blogs/news/`, limited | `/guides/` with the same SSR treatment. Better, but must be built |
| Review schema | App-provided, often fabricated | Emitted only when real. Keep this discipline |
